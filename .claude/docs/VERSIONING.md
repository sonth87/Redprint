# Versioning — package version bump rules

> **Mandatory when editing code that ships from `packages/*` or `apps/*`.** Monorepo → each package
> versions independently, managed with **Changesets** + **SemVer**.

## Not to be confused with `schemaVersion`

This file governs **npm package versions** (`package.json`'s `"version"`, tracked via Changesets).
It has nothing to do with `BuilderDocument`'s `schemaVersion` (the JSON document format persisted
documents carry) — that has its own independent SemVer lifecycle and migration engine, documented in
[COMMAND_SYSTEM.md § Schema Versioning & Migration](./COMMAND_SYSTEM.md#schema-versioning--migration).
A change can trigger one, both, or neither:

- Editing `builder-editor`'s canvas code → package version only.
- Adding a field to `BuilderDocument` → `schemaVersion` bump + migration, and typically a package
  version bump for whichever package owns the type (usually `builder-core`).
- Never conflate the two version numbers or reuse one field's bump rationale for the other.

## Principles

- **SemVer** `MAJOR.MINOR.PATCH` per package under `packages/*` and `apps/*`.
- **Changesets** is the tool of record: every change worth shipping gets one changeset file
  describing it + the bump level, per affected package. Version bumps and `CHANGELOG.md` entries
  are generated at release time, not written by hand.
- **Never hand-edit `version` in a `package.json`** once Changesets is in place — let
  `changeset version` do it. Exception: initial adoption (one-time backfill).
- **Never hand-edit a package's generated `CHANGELOG.md`** — same reasoning; fix the source
  changeset instead if a description is wrong before release.

## Bump levels

| Level | When | Example |
|---|---|---|
| **PATCH** (0.1.**0**→0.1.**1**) | Bug fix, internal change, no API change | style fix, calculation fix, perf improvement |
| **MINOR** (0.**1**.0→0.**2**.0) | New feature, backward compatible | new component, new optional prop, new command |
| **MAJOR** (**0**.1.0→**1**.0.0) | Breaking change | renamed/removed exported type, changed command payload shape, removed public API |

**Project-specific cases:**

- Changing an interface contract documented in `README.md` (§ "Full Technical Specification") or in
  `ARCHITECTURE.md`'s type contracts → those are declared **immutable unless version-bumped** — treat
  as **MAJOR** for the owning package.
- Changing a `ComponentDefinition`'s `propSchema` in `builder-components` in a way that changes
  existing prop meaning/type → **MAJOR** for `@ui-builder/builder-components`. Adding a new optional
  prop → **MINOR**.
- Changing the AI command whitelist (`command-reference.ts` / `allowedCommands.ts`, see the
  three-way sync rule in the root `CLAUDE.md`) → **MINOR** for `@ui-builder/builder-editor` /
  `@ui-builder/api` if additive, **MAJOR** if a command's payload shape changed or a command was
  removed.
- Changes confined to `apps/*` (playground, website, cms, api) that don't touch a published
  `packages/*` contract → bump only that app's own version; do not cascade to unrelated packages.

## Workflow (AI agents and humans)

Applies to any change worth a changelog entry — a bug fix that changes behavior, a new feature, a
breaking change. **Does not apply** to comment-only edits, formatting, or pure internal refactors
with no observable behavior change.

1. After finishing the code change, create a changeset:
   ```bash
   pnpm changeset            # select affected package(s) + bump level + description
   ```
   The description you write here becomes the `CHANGELOG.md` entry — write it for someone reading
   the changelog later, not as an internal note.
2. Commit the code changes together with the generated `.changeset/*.md` file in the same commit —
   a change and its changeset must not be split across commits.
3. **Do not run `changeset version` or `changeset publish` yourself.** Bumping `package.json` and
   generating `CHANGELOG.md` entries is a release step the maintainer triggers deliberately:
   ```bash
   pnpm changeset version    # bump versions + generate CHANGELOG.md (maintainer-run)
   pnpm changeset publish    # publish, if/when packages are published (maintainer-run)
   ```

## Root `CHANGELOG.md`

The root `CHANGELOG.md` predates Changesets adoption and was hand-written against a single
whole-repo version number (`0.1.0`). Going forward, per-package `CHANGELOG.md` files generated by
Changesets (one per package under `packages/*`/`apps/*`) are the source of truth for what shipped in
each package. Leave the existing root file's history as-is; do not hand-append new entries to it —
new entries belong in the generated per-package changelogs instead.
